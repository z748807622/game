# 猜数字（双人）示例游戏

用这套中继服务器做的第一个完整游戏：两人各设一个 4 位暗号，轮流猜对方的，每次只告诉你「数字和位置同时对上几个」，先凑齐 4 个的人赢。

**服务端零改动**——没有新增 op、没有解析 payload，只把三个静态文件 `go:embed` 进二进制。这正好演示了设计边界：房间、转发、重连、补发由服务器负责，游戏规则全在客户端。

## 打开

```bash
go run ./cmd/server            # 默认监听 :8080
```

- 本机：<http://localhost:8080/bulls.html>
- 手机和电脑连同一局域网：`http://<电脑局域网IP>:8080/bulls.html`（默认 `:8080` 已监听所有网卡，防火墙需放行）

两个页面即可对战：一人「创建房间」拿到 4 位房间码，另一人输入房间码「加入」。

## 规则

| 项 | 规则 |
|----|------|
| 人数 | 固定 2 人；满 2 人自动锁房，第三人被 `ROOM_LOCKED` 挡在门外 |
| 暗号 | 4 位数字，1000–9999；**数字可重复**，首位不能是 0 |
| 反馈 | 只报「数字和位置同时正确的位数」，0–4（不报 B 位） |
| 回合 | 严格轮流，每次猜一次 |
| 胜负 | 反馈为 4 即胜，单局定胜负 |
| 续局 | 「再来一局」双方重设暗号；首局房主先猜，之后每局交替先手 |

## 为什么没有服务端逻辑

服务器不解析 payload，就无法当裁判，所以：

**裁判权 = 暗号持有者。** 谁被猜，谁在自己浏览器里算 `hits` 并广播判定结果。这样胜负只有一个事实来源，猜的人无法自己宣布赢；代价是裁判的客户端可以作弊——与项目既定边界一致（朋友间玩，不做反作弊）。

暗号**只存在各自的内存里**，任何消息都不带它；只有对局结束后双方各公开一次自己的暗号，界面才能亮出双方答案。

## 消息（payload JSON v1）

服务端看到的只是一段不透明字节，下面是游戏自己的约定：

| 方向 | 消息 | 说明 |
|------|------|------|
| 广播 | `{t:'secret', round}` | 暗号已就绪，**不带暗号** |
| 房主 | `{t:'start', round, turn}` | 双方就绪后开局，指定先手 |
| 猜方 | `{t:'guess', round, n:'1234'}` | 一次猜测 |
| 裁判 | `{t:'judge', round, by, guess, hits, win, winner, next}` | 唯一权威事实；`hits=4` 时 `win=true`、`winner=猜方` |
| 房主 | `{t:'rematch', round}` | 下一局，局号 +1 |
| 任意 | `{t:'sync_req'}` / `{t:'sync', state}` | `RESYNC` 后的全量快照（不含暗号） |
| 结算 | `{t:'reveal', round, secret}` | 对局结束后公开自己的暗号 |

`round` 用来丢弃迟到消息：局号不符一律忽略，避免旧局的 `judge` 污染新局，也避免重复的 `start` 把局面改乱。

## 三个关键实现决策

### 1. 每条消息都带上自己（回显）

房间级 `seq` 对每条 `RELAY` 递增，但帧只投给 `targets`。双人对局里如果一条消息只发给对手，发件人自己就收不到这一帧，双方各自看到的 `seq` 会跳号——`RelayClient` 会据此判定「空洞」并断开重连（4000），消息就丢了。

所以游戏里所有消息的 `targets` 都包含「自己 + 对手」：两个成员都收到每一帧，`seq` 连续；自己的回显在 `onPayload` 里按 `from === selfSlot` 忽略。

### 2. 双方只信 `judge`

猜方不自己算结果，收到 `judge` 才更新历史；裁判自己也把同一条 `judge` 喂给同一个状态机。于是两端的历史、回合、胜负逐字段一致，e2e 测试直接断言 `deepStrictEqual(history)`。

状态机在 [`web/bulls-core.js`](../web/bulls-core.js)（纯函数、无 DOM、无 WebSocket）：

```
setup --secret×2--> setup --start--> playing --judge(hits<4)--> playing
                                        └--judge(hits=4)--> over --rematch--> setup(round+1)
```

### 3. 断线靠补发，补发不够靠快照

- 普通断线：`RelayClient` 带 `sid + lastSeq` 重连，服务端补发；游戏层状态仍在内存里，不用重建。
- 补发窗口不足：服务端发 `RESYNC`，客户端广播 `sync_req`，对手回 `sync` + `snapshot()`（回合、历史、胜负、就绪标记，**不含暗号**）。

## 已知限制（都是刻意的）

1. **刷新页面 = 重新加入**：`sid` 和暗号都在内存里，刷新后是新会话、新 slot，本局作废，需重开。
2. **可作弊**：裁判的浏览器可以改判定结果；不解析业务消息就无法校验，这是本项目的前提。
3. 没有计时、没有累计比分、没有 AI 对手。
4. 第三人被锁定在门外，不提供观战。

## 测试

```bash
node web/test/bulls-core.test.js     # 纯逻辑：校验 / hits / 状态机 / 快照
node web/test/bulls-e2e.test.js      # 真服务器 + 两个客户端打两局（需先起服务）
node web/test/bulls-ui.test.js       # Chrome headless：手机 390×844 + 桌面 1440×900
```

Makefile 里对应 `make test-js`（含内核用例）、`make e2e-game`、`make ui-game`。

UI 测试会检查：无页面异常、无横向溢出（`scrollWidth <= clientWidth`）、关键按钮高度 ≥44px、结算亮出双方暗号、再来一局后双方回到设暗号，并产出截图 `.tmp/bulls-mobile.png`、`.tmp/bulls-desktop.png`。

Node 18 没有全局 `WebSocket`，测试用 [`web/test/ws-polyfill.js`](../web/test/ws-polyfill.js) 顶上（零依赖）；浏览器里当然用原生 `WebSocket`。

## 排错

**改了 `web/` 下的文件必须重启服务。** `go:embed` 是编译期把文件烘焙进二进制，`go run` 的进程不会读你磁盘上的新文件——否则会出现「代码明明改了、页面还是旧行为」。
