# 多人纵版打飞机（合作优先）设计与联机方案

> 状态：M1 合作原型已实现（2026-11-26），PvP 未开始。设计 v1 与代码一致。
> 关联：[中继设计](room-relay-design.md) · [协议 v2](protocol-v2.md) · [客户端接口](api-reference.md) · [猜数字示例](bulls-game.md)
> 目标：复用现有房间中继服务器，做 2–4 人实时合作纵版射击；PC 鼠标跟随、移动端点击/拖动控制。

## 0. 结论先行

**能，不改后端逻辑也能做。**

- 不新增 op、不解析 payload、不改房间/转发/重连/补发；服务器仍然只负责「谁在哪个房间」和搬字节。
- 实现轮唯一的 Go 改动：在 [web/embed.go](../web/embed.go) 的 `go:embed` 文件名清单里加一行，把新页面装进二进制。服务端逻辑与协议零改动。
- 游戏逻辑全在客户端：**主机权威** + 30Hz 模拟 + 15Hz 全量快照 + 30Hz 目标点输入。
- 成本：2 人典型 **0.29 Mbps**、3 人典型 **0.46 Mbps** 服务器出网/房；100 房约 29 / 46 Mbps。实时局比桌游重约百倍，容量要按 **200–500 房实测**再定，不能沿用「3000 房」的目标。
- 最容易踩的坑：**所有游戏消息必须广播给全房每个成员（含自己、含离线成员）**，否则 `RelayClient` 会因房间 `seq` 空洞误判而断开重连（[bulls.js](../web/bulls.js) 已踩过）。

## 1. 定位与边界

### 1.1 要做什么

- 2–4 人合作纵版弹幕射击：共享分数、各自命数、一起打波次和 Boss。
- PC：鼠标跟随；移动端：点按/拖动屏幕。飞机以固定最大速度追目标点，**不随鼠标速度变速、不瞬移**。
- 断线自动重连；短暂断线由服务器补发，补发窗口不足时由下一帧全量快照自愈。
- 2 台手机同一局域网即可开房对战（合作）。

### 1.2 明确复用

| 能力 | 由谁负责 | 是否改动 |
|---|---|---|
| WebSocket 接入、鉴权、限流 | `internal/server` | 否 |
| 房间码、密码、锁房、踢人、房主转移 | `internal/room` / `internal/registry` | 否 |
| 房间级 `seq`、环形重放、断线宽限 | `internal/room` | 否 |
| 二进制中继信封 | `internal/protocol` | 否 |
| 浏览器协议库 | [web/relay.js](../web/relay.js) | 否（直接复用） |
| 静态页面托管 | [web/embed.go](../web/embed.go) | **加一行文件名** |

### 1.3 明确接受的边界

- **无权威 → 可作弊**：服务器看不懂游戏消息，主机可以改分/改血；只适合朋友间娱乐，不做竞技、不接虚拟货币。
- **单机内存态**：进程重启所有房间消失，本局作废。
- **仅 WebSocket**：没有 TCP/KCP/UDP，实时局走 TCP 上的 WS；不追求 FPS 级公平。
- **不做**：匹配、房间列表、观战（M4）、持久化、回放（M4）、反作弊、语音。

## 2. 为什么是主机权威

### 2.1 四种方案对比

| 方案 | 客户端延迟 | 带宽/房 | 一致性 | 实现复杂度 | 作弊 |
|---|---|---|---|---|---|
| **主机权威（选定）** | 自己 0ms（本地预测），队友约 1 个快照间隔 + RTT | 中（~10–30 KB/s/客户端） | 单一事实来源 | 低 | 主机可作弊 |
| 帧同步 / lockstep | 输入缓冲 100–200ms | 极低（只传输入） | 依赖完全确定性 | 高 | 全员可改输入 |
| 各自为战（各算各的） | 0ms | 低 | 敌人/伤害会分叉 | 中 | 高 |
| WebRTC P2P | 最低 | 不经过服务器 | 需要房主权威 | 高（信令/NAT） | 同主机权威 |

### 2.2 为什么不选帧同步

- JS 浮点跨浏览器/设备并不保证一致：`Math.sin/cos/atan2` 的实现、舍入、JIT 都可能不同；要做就得把所有物理改成定点整数，工作量翻倍。
- 需要输入缓冲（100–200ms）来吸收抖动，手感明显变重；一人卡顿，全员停帧。
- 重连要把输入日志从开局重放；64KB 的环形缓冲装不下几分钟的输入，得自己传快照，等于又回到主机权威。
- 服务器不解析 payload，帧同步也挡不住改输入；作弊问题并没有解决。

### 2.3 为什么不选 P2P

- 不改后端就没有信令通道；手动交换 SDP 不现实。
- NAT/防火墙穿透不可靠，移动网络下成功率更低。
- 房主仍然要权威，省下的只是「一跳中继」，却换来一堆连接失败和排错成本。

### 2.4 主机权威的代价与缓解

- **主机有轻微优势**：主机输入不经过网络；合作 PvE 无对抗，可接受。M3 做 PvP 时再用「固定输入延迟 / 轮换房主 / BO3」缓解。
- **主机切后台会暂停全场**：用「显式暂停 + 队友快照饥饿提示」处理（见 §10）。
- **队友位置有 RTT 级滞后**：主机用 30Hz 目标点 + 同一套追踪积分，客户端本地预测 + 快照软校正；玩家判定半径只取 4px，掩盖小误差（见 §4、§9）。

## 3. 联机拓扑与数据流

### 3.1 拓扑

```
                  ┌──────────────────────────────┐
  玩家 A（主机）──┤                              │
  玩家 B ─────────┤  WebSocket  /ws              │
  玩家 C ─────────┤  Relay Room Actor            ├── 按 targets 扇出（只搬字节）
                  │  成员表 / seq / 64KB 环形重放 │
                  └──────────────────────────────┘
```

- 一条连接 = 一个房间成员；房间归属由连接状态决定，游戏消息里不带 roomId。
- 游戏主机 = **中继房主**（`client.host`，`HOST` 事件）。只有主机跑模拟、判碰撞、算分。
- 队友不跑世界模拟，只做：本地预测自己的飞机、插值渲染、发送目标点。

### 3.2 一帧的生命周期

1. 队友 30Hz 发 `INPUT{targetX, targetY}`；主机 30Hz 发 `SNAP`、开局发 `START`。
2. 每条游戏消息都通过 `RelayClient.relayBytes()` 发出，`targets = 当前房间全部成员的 slot`（含自己、含离线成员）。
3. 服务器 `handleRelay` 校验 target、`seq++`、组装一次 `RELAY{from, seq, payload}`，向所有在线 target 共享同一份只读切片。
4. 客户端收到 `RELAY`：按首字节 magic 过滤，按 `type` 解包；自己的回显按 `from === selfSlot` 忽略。
5. 主机处理所有 `INPUT`，每 tick 只取每个槽位最新的目标点；其他人忽略 `INPUT`。

### 3.3 为什么必须广播给全员

房间 `seq` 是**房间级**的，每条 `RELAY` 都 +1。`RelayClient` 用 `lastSeq` 检测空洞：

```js
if (this.lastSeq !== 0 && msg.seq !== this.lastSeq + 1) {
  this.emit('gap', ...);
  this.forceReconnect();   // 4000
}
```

如果输入只发给主机：

- 队友 B 收不到队友 C 的输入帧，但会收到主机的快照（seq 已经跳过 C 的那一帧）；
- B 看到 `seq` 跳号 → 判定空洞 → 主动重连 → 丢帧。

所以规则只有一条：**每条游戏消息的 targets 都包含房间当前全部成员（含发送者自己，含离线成员）**。

- 含自己：自己的 `lastSeq` 才会随自己发出的帧前进。
- 含离线成员：帧才会进 64KB 环形缓冲，重连时才能补发。
- 代价：输入扇出是 `N²`（3 人局约 6.5 KB/s），相对快照可以忽略（见 §5）。

### 3.4 为什么快照是全量而不是增量

- **RESYNC 自愈**：补发窗口不足时，服务端只发 `RESYNC`、不补发；客户端清空插值缓冲，等下一帧全量快照即可，不需要游戏层再发「请给我快照」。
- **重连简单**：服务端补发的旧帧和新帧都是全量，按 `tick` 丢弃旧的、应用新的，不需要维护 delta 基线。
- **漏帧安全**：任何一帧丢失，下一帧就能恢复；不需要 ACK/重传。
- 代价：每帧约 0.5–1.9KB，15Hz。按 §5 计算完全可接受。

### 3.5 帧预算

- 3 人局每客户端每秒收到：3×30（所有输入）+ 15（快照）= **105 帧/s**；4 人局 **135 帧/s**。
- 每条帧都有 8B 中继头 + 2B from + 4B seq 的固定开销；业务 payload 本身是小包。
- 服务端入站只看「本连接发了多少帧」：队友 30/s，主机 45/s，远低于默认 200 帧/s 限流。

## 4. 控制模型（PC 鼠标 / 移动端点击拖动）

### 4.1 一句话

**鼠标/手指只负责指定目标点 `aim`；飞机以固定最大速度 `maxSpeed = 300 px/s` 追过去。**

不是「鼠标动多快飞机就多快」，也不是「瞬移到鼠标位置」。鼠标横跨半个屏幕，飞机也是以 300px/s 飞过去。

### 4.2 统一积分

客户端本地预测和主机模拟用**同一个函数**：

```js
// 每 tick / 每帧调用；pos、aim 都是世界坐标（px）
function seek(pos, aim, maxSpeed, dt) {
  const dx = aim.x - pos.x;
  const dy = aim.y - pos.y;
  const dist = Math.hypot(dx, dy);
  if (dist <= 0.5) return { x: pos.x, y: pos.y };      // 死区，避免抖动
  const step = Math.min(dist, maxSpeed * dt);          // 关键：步长上限
  return {
    x: pos.x + (dx / dist) * step,
    y: pos.y + (dy / dist) * step
  };
}
```

- 不越界：`aim` 与积分结果都钳到 `[16, W-16] × [16, H-40]`。
- 不过冲：`step = min(dist, maxSpeed*dt)`，到达前不减速，到达后停。
- 速度不随指针速度变化：指针只是更新 `aim`，不影响 `maxSpeed`。
- 主机端：`dt = 1/30`，用收到的最新 `aim` 跑同一个 `seek`；队友端：`dt` 取渲染帧间隔（上限 50ms），本地预测。

### 4.3 PC：鼠标跟随

- `pointermove`（鼠标）更新 `aim = 屏幕坐标 → 世界坐标`。
- 指针离开画布：保留最后 `aim`，飞机继续飞完再停。
- 鼠标点击不额外处理；点击和移动等价。
- 不做「鼠标速度 → 飞机速度」映射，也不做「鼠标位置 = 飞机位置」的硬绑定。

### 4.4 移动端：点击 / 拖动

- `pointerdown` / `pointermove`（触摸）更新 `aim`。
- `pointerup` / `pointercancel` 后保留最后 `aim`，飞机继续以最大速度飞到该点再停。
- 画布设 `touch-action: none`，`pointerdown` 时 `preventDefault()`，避免页面滚动、双击缩放、长按菜单。
- 手指可能遮住飞机：M1 先接受「飞机以速度上限落后于手指」；M2 视手感加固定偏移或虚拟摇杆（见 §15）。

### 4.5 坐标换算

画布按逻辑世界 `480×720` 绘制，CSS 尺寸自适应；指针坐标必须过 `getBoundingClientRect()` 换算，不能直接用 `clientX`：

```js
const rect = canvas.getBoundingClientRect();
const aim = {
  x: ((ev.clientX - rect.left) / rect.width) * WORLD_W,
  y: ((ev.clientY - rect.top) / rect.height) * WORLD_H
};
```

- 画布内部按 `devicePixelRatio` 设置 backbuffer，绘制时统一缩放，逻辑坐标不变。
- 桌面宽屏时画布居中留黑边（letterbox），换算已经包含 rect 宽高，自动正确处理。
- 触摸的 `pointerId` 只跟踪第一个按下的指针，避免多指互相抢目标点。

### 4.6 行为速查

| 操作 | 结果 |
|---|---|
| 鼠标缓慢移动一小段 | 目标点离飞机很近，飞机小步跟随；本质仍是追目标点，不是按鼠标速度映射 |
| 鼠标快速甩到远处 | 飞机以 300px/s 飞过去，不瞬移 |
| 鼠标停住 | 飞机飞到光标处停下 |
| 鼠标移出画布 | 保留最后目标点，飞完停下 |
| 手机点一下远处 | 飞机以 300px/s 飞向该点 |
| 手机按住拖动 | 目标点持续更新，飞机追随 |
| 手机松手 | 保留最后目标点，飞完停下 |
| 主机收到队友目标点 | 同一套 `seek`，按 30Hz 积分；位置由主机快照下发 |

### 4.7 输入包只送目标点

- `INPUT` 里是 `targetX/targetY`（1/4px 定点），不是速度、不是位移、不是鼠标轨迹。
- 丢包安全：目标点是绝对量，迟到的旧包不会让飞机「倒退」，最新到达的包覆盖即可。
- 主机不信任队友的位置，只信任「意图」；主机自己积分、自己钳边界，队友无法瞬移（最多在速度上限内移动）。

## 5. 帧率、带宽与容量

### 5.1 固定参数

| 参数 | 值 | 说明 |
|---|---|---|
| 模拟频率 | **30 Hz** | 主机固定步长 `dt = 1/30s` |
| 快照频率 | **15 Hz** | 每 2 tick 一帧全量快照 |
| 输入频率 | **30 Hz** | 每位玩家每 tick 发一次目标点 |
| 世界尺寸 | 480×720 | 逻辑像素；定点 1/4px |
| 玩家速度 | 300 px/s | `seek` 的最大速度 |
| 房间人数 | 2–4（允许单人试玩） | 满 4 自动锁房 |
| 快照实体上限 | 4 玩家 / 24 敌机 / 160 敌弹 / 64 我弹 | 超过则丢最旧的子弹 / 不再生成 |
| 快照最大 | **1911 B** | 4 玩家 + 全上限实体 |

### 5.2 计算前提

- 单帧线上字节 = 业务 payload + 中继信封 14B（8B 头 + from 2B + seq 4B）+ WS 帧头 2–4B。
- **不含 TCP/IP/TLS**；实际网卡流量在此基础上约 +5%～15%（见 5.5）。
- 输入帧 payload 8B → 线上 24B；快照按 §6 的布局计算。
- 场景定义：
  - 轻（前几波）：6 敌机 / 40 敌弹 / 20 我弹
  - 中（中期）：12 / 90 / 40
  - Boss（高压）：18 / 140 / 60
  - 上限：24 / 160 / 64

### 5.3 单房带宽（2 / 3 人）

| 人数 | 场景 | 快照 payload | 服务器出网 | 服务器入网 | 每玩家下行 | 房主上行 | 出网/小时 |
|---|---|---|---|---|---|---|---|
| 2 | 轻（前几波） | 537 B | 19.1 KiB/s · **156 kbps** | 9.5 KiB/s · 78 kbps | 78 kbps | 72 kbps | ~70 MB |
| 2 | 中（中期） | 1101 B | 35.6 KiB/s · **292 kbps** | 17.8 KiB/s · 146 kbps | 146 kbps | 140 kbps | ~131 MB |
| 2 | Boss/高压 | 1665 B | 52.1 KiB/s · **427 kbps** | 26.1 KiB/s · 214 kbps | 213 kbps | 208 kbps | ~192 MB |
| 2 | 上限 | 1891 B | 58.7 KiB/s · **481 kbps** | 29.4 KiB/s · 241 kbps | 241 kbps | 235 kbps | ~217 MB |
| 3 | 轻（前几波） | 547 B | 31.2 KiB/s · **255 kbps** | 10.4 KiB/s · 85 kbps | 85 kbps | 74 kbps | ~115 MB |
| 3 | 中（中期） | 1111 B | 55.9 KiB/s · **458 kbps** | 18.6 KiB/s · 153 kbps | 153 kbps | 141 kbps | ~206 MB |
| 3 | Boss/高压 | 1675 B | 80.7 KiB/s · **661 kbps** | 26.9 KiB/s · 220 kbps | 220 kbps | 209 kbps | ~298 MB |
| 3 | 上限 | 1901 B | 90.7 KiB/s · **743 kbps** | 30.2 KiB/s · 248 kbps | 248 kbps | 236 kbps | ~334 MB |

读表：

- **典型局**：2 人约 0.29 Mbps、3 人约 0.46 Mbps 出网；Boss 期约 0.43 / 0.66 Mbps；打满上限约 0.48 / 0.74 Mbps。
- **3 人约为 2 人的 1.55–1.6 倍**，不是 1.5 倍：快照多一份，输入是 `N²` 扇出。
- **队友上行只有约 6 kbps**（30 × 24B）；房主上行 0.14–0.24 Mbps（一份快照）。
- **服务器入网约为出网的 1/3–1/2**；计费通常看出网，按出网列估算。
- 带宽大头是快照；输入帧即使广播给全员，也只占约 5%–20%（前期子弹少时占比最高）。

### 5.4 放大到并发房（只看出网）

| 并发房数 | 2 人典型 | 2 人上限 | 3 人典型 | 3 人上限 |
|---|---|---|---|---|
| 100 | 29 Mbps | 48 Mbps | 46 Mbps | 74 Mbps |
| 1000 | 292 Mbps | 481 Mbps | 458 Mbps | 743 Mbps |

- 带宽层面，1Gbps 网卡能撑约 1000 个「3 人典型房」，但 1000 个「3 人上限房」会接近打满。
- **更早撞到的通常是 CPU/写 syscall**：3 人房每秒约 105 条消息 × 3 个目标 = **315 次 WS 写/s**；1000 房就是 31.5 万次写/s。2 人房约 150 次写/s。
- 因此容量结论：**先按 200–500 房做压测**，用真实的快照/子弹数量校准，不要直接承诺 3000 房。

### 5.5 叠加开销

以上是「业务帧 + 中继信封 + WS 头」。真实链路上还有：

- TCP/IP：每段约 40B；如果每帧单独成段，小帧的占比会很高（输入帧 24B → 64B+）。
- TLS（wss）：每条记录约 5B 头 + 16B AEAD tag；大帧可忽略，小帧占比明显。
- 中继服务器自身的日志/心跳/健康检查。
- 经验值：按上表再 **+5%～15%** 做容量预留；移动网络差时重传会额外放大。

### 5.6 和原目标的关系

中继设计的目标是「3000 房 / 2w 连接 / 2w msg/s」，那是桌游/狼人杀量级（每房每秒几条消息）。实时打飞机是：

- 带宽：约 15–30 KB/s/客户端（典型–上限），是桌游的百倍量级；
- 帧数：3 人房 315 次写/s，是桌游的几十倍。

所以**沿用协议的容量数字，但重新压测**；实时局的上限更可能由出口带宽和每帧写次数决定，而不是房间数。

## 6. 载荷 v1（二进制线格式）

### 6.1 总则

- 游戏 payload 对中继不透明；整包放在一条 `RELAY` 里，**不要**再套一层中继消息。
- 全部小端；定长字段；无变长编码/压缩。
- 首字节 magic `0x50`（字符 `P`），用于把游戏 payload 和未来的其他 payload 区分开；不认识的 magic / type **静默忽略**，不断开。
- `ver` 目前为 1；不兼容变更时 +1，双方按 `ver` 分支或直接忽略。
- 单帧 payload 建议 ≤ 60KB；本设计最大 1911B。

### 6.2 通用头

```
偏移  长度  字段    说明
0     1    magic   0x50 ('P')
1     1    ver     1
2     1    type    1=INPUT, 2=SNAP, 3=START
```

### 6.3 INPUT（8B，每位玩家 → 全体，30Hz）

```
偏移  长度  字段      说明
0     1    magic     0x50
1     1    ver       1
2     1    type      1
3     2    targetX   目标点 x，u16，1/4px，0..1920
5     2    targetY   目标点 y，u16，1/4px，0..2880
7     1    flags     预留；bit0=请求炸弹，v1 恒 0
```

- 发送的是**目标点**，不是速度/位移。
- 主机只取每个槽位最新的一条；去重、钳边界、按速度上限积分。
- 队友自己的回显按 `from === selfSlot` 忽略。

### 6.4 START（22B，主机 → 全体，每局一次）

```
偏移  长度  字段         说明
0     1    magic        0x50
1     1    ver          1
2     1    type         3
3     4    seed         本局随机种子（主机侧生成；客户端只用于显示/回放预留）
7     1    mode         0=合作，1=PvP（M3 预留）
8     1    maxWave      本局通关波次（默认 15）
9     1    playerCount  1..4
10    ...  玩家列表     每项 3B：u16 slot + u8 colorIndex
```

- `START` 是「换局/重开」的显式信号；漏掉也不致命，全量 `SNAP` 自带 `phase/wave/score`，客户端可自举（见 §9.4）。
- 玩家列表按 slot 升序；`colorIndex` 决定机身颜色。

### 6.5 SNAP（20B 头 + 实体，主机 → 全体，15Hz）

```
偏移  长度  字段         说明
0     1    magic        0x50
1     1    ver          1
2     1    type         2
3     4    tick         全局单调 tick（30Hz，跨局不重置）
7     1    phase        0=大厅 1=对局 2=结算
8     1    flags        bit0=win；其余预留
9     2    wave         当前波次
11    4    score        共享分数
15    2    bossHp       Boss 剩余血；0=无 Boss
17    2    bossMaxHp    Boss 最大血；0=无 Boss
19    1    playerCount  0..4

玩家项（10B × playerCount）：
  0   2  slot
  2   2  x          1/4px
  4   2  y          1/4px
  6   1  hp         0..3
  7   1  lives      0..3
  8   1  state      0=存活 1=无敌 2=倒地 3=观战
  9   1  flags      bit0=在线(connected) bit1=开火中

敌机段：
  1B enemyCount（0..24）
  每项 9B：u16 id, u8 kind, u16 x, u16 y, u8 hp, u8 flags(bit0=boss)

敌弹段：
  1B ebulletCount（0..160）
  每项 7B：u16 x, u16 y, i8 vx, i8 vy, u8 kind

我弹段：
  1B pbulletCount（0..64）
  每项 8B：u16 x, u16 y, i8 vx, i8 vy, u8 ownerSlot, u8 kind
```

- `tick` 单调递增：重连补发的旧帧、上一局残留帧都能用 u32 无符号差值安全丢弃（见 §9.5）。
- 快照 **全量**：每帧都是当前完整世界，不做 delta。
- 敌机有稳定 `id`，用于客户端插值和击杀特效；子弹不需要 id（按最新帧 + 速度外推，见 §9.3）。
- 玩家 `flags.bit0` 为 0 表示宽限期内断线：队友仍能看到位置，但不受击、不开火。
- 最大尺寸：20 + 4×10 + 1 + 24×9 + 1 + 160×7 + 1 + 64×8 = **1911 B**。

### 6.6 定点与速度单位

| 量 | 编码 | 说明 |
|---|---|---|
| 位置 | `u16`，1/4 px | 世界 480×720 → 0..1920 / 0..2880，u16 足够 |
| 速度 | `i8`，px/tick（30Hz） | 实际 px/s = `v × 30`，范围 ±3810 px/s，精度 30 px/s |
| 时间 | `u32` tick | 30Hz 单调；约 4.5 年回绕，客户端用无符号差值比较，START/重连时重置基线 |
| 计数 | `u8` | 受硬上限约束，不会溢出 |

- 子弹速度只用于客户端外推和视觉，不参与客户端碰撞判定，精度足够。
- 服务端不解析 payload，以上全部是游戏层约定。

### 6.7 版本演进

- 新增 type：旧客户端按未知 type 忽略，安全。
- 修改现有 type 的字段：必须升 `ver`；旧客户端遇到不认识的 `ver` 忽略。
- 永远不要复用旧 type 编号表达新语义。
- 客户端对截断/越界包必须容错：丢弃该帧并继续，不要抛异常终止对局。

## 7. 游戏规则 v1

### 7.1 世界与玩家

- 纵版卷轴，世界 480×720；自动开火，玩家只需要移动。
- 玩家：3 HP / 3 命；视觉尺寸约 22×26，**判定半径 4px**（弹幕游戏惯例，手感更宽容）。
- 碰到敌弹/敌机：HP-1，进入 90 tick（3s）无敌；HP=0 → 倒地，命-1，90 tick 后在底部中央重生；命=0 → 观战，不再复活。
- 重生/回到对局后给 60 tick 无敌 + 闪烁。
- 全员观战 → 判负；15 波通关 → 判胜。

### 7.2 自动开火

- 存活且 `phase=playing` 时每 6 tick（5 发/s）发射 1 发，速度 660 px/s 向上，伤害 1，半径 3。
- 火力升级/道具不在 v1，放 M2（协议已预留 `pbullet.kind`）。

### 7.3 敌机

| kind | 名称 | HP | 速度 | 行为 | 半径 | 分数 |
|---|---|---|---|---|---|---|
| 0 | 小兵 | 1 | 120 | 直线下落 | 12 | 10 |
| 1 | 蛇形 | 2 | 100 | 正弦横摆，振幅 60 | 12 | 20 |
| 2 | 精英 | 6 | 90 | 每 90 tick 朝最近玩家瞄准射击 | 16 | 50 |
| 3 | Boss | 120×成长 | 30（入场 90） | 入场后悬停，环形+瞄准弹幕 | 40 | 500 |

- 敌弹速度 150–320 px/s，按 kind 区分弹型（直线/瞄准/散射/环形）。
- 敌机/敌弹出界（留 40px 余量）即回收。
- 硬上限：敌机 24、敌弹 160、我弹 64；超限时不再生成，敌弹超限丢最旧的。

### 7.4 波次与 Boss

- 第 `n` 波：敌机预算 `min(24, 6 + 2n)`，生成间隔 `max(12, 26 - 2n)` tick（约 0.4–0.8s）。
- 每 5 波出 Boss（`n % 5 == 0`）；Boss 波只生成 Boss，不刷普通小兵（护卫 M2 再加）。
- 清空当前波所有敌机且生成队列为空 → 60 tick 间隔 → 下一波。
- 难度成长：敌机 HP ×`(1 + 0.08(n-1))`，弹速 ×`(1 + 0.03(n-1))`。
- 主机侧所有随机（刷怪种类、弹幕角度、掉落）走 `mulberry32(seed)`，不直接用 `Math.random`；视觉粒子可用本地随机。
- 第 15 波 Boss 被击杀 → `phase=over, win=true`。
- 全员观战（命尽）→ `phase=over, win=false`。

### 7.5 分数

- 击杀分数：小兵 10 / 蛇形 20 / 精英 50 / Boss 500；全员共享一个 `score`。
- 不做连击、不做个人分（v1 保持简单；M2 可加）。

### 7.6 常量汇总

| 常量 | 值 |
|---|---|
| TICK_HZ | 30 |
| SNAP_EVERY | 2 tick（15Hz） |
| INPUT_HZ | 30 |
| WORLD | 480×720 |
| PLAYER_SPEED | 300 px/s |
| PLAYER_HIT_R | 4 px |
| PLAYER_HP / LIVES | 3 / 3 |
| INVULN / RESPAWN | 90 / 90 tick |
| FIRE_INTERVAL | 6 tick |
| BULLET_SPEED | 660 px/s |
| MAX_WAVE | 15 |
| BOSS_EVERY | 5 波 |
| CAPS | 4 / 24 / 160 / 64 |
| STARVE_MS | 600（快照饥饿判定） |
| INTERP_MS | 80（插值延迟） |
| EXTRAP_MAX_MS | 150（外推上限） |

## 8. 房间流程与状态机

### 8.1 游戏层状态机

```
LOBBY ──房主 START──▶ PLAYING ──全员命尽 / 15 波通关──▶ OVER
  ▲                      │                              │
  │                      └──房主离开 / HOST 转移──▶ 本局作废，回 LOBBY
  └────────────────────── OVER 后「再来一局」/ 全员离房 ──┘
```

- `LOBBY`：已进房，显示成员、房间码、开始按钮（仅房主）。
- `PLAYING`：收到 `START` 或第一帧 `phase=playing` 的快照。
- `OVER`：`phase=over` 的快照；显示胜负、分数、波次。
- 房主离开/超时导致 `HOST` 转移时：所有客户端把本局标记作废，回大厅；**不做主机迁移**（新房主没有世界状态）。

### 8.2 建房 / 加入 / 锁房

- 复用现有 `CREATE` / `JOIN` / `LOCK` / `KICK`：
  - 大厅里满 4 人 → 房主自动 `lock(true)`（第 5 人 `ROOM_LOCKED`）。
  - 开局时再 `lock(true)`；结算 `lock(false)`，允许新人加入下一局。
- 密码沿用现有 4 位房间码 + 可选密码；meta 里放 `{name}`。
- 玩家列表：当前**在线**成员按 slot 升序取前 4 个；`colorIndex` = 列表下标。允许单人开局用于调试/试玩，正常玩法 2–4 人。
  - 极端竞态下如果锁房前已有第 5 人加入：开局只取 slot 最小的 4 人，其余为只读观战（接收快照、不发输入）；下局可加入。v1 不做正式观战 UI（M4）。
- 房主自己不特殊：也是玩家之一。

### 8.3 开局与再来一局

- 房主点「开始游戏」→ 广播 `START{seed, mode=0, maxWave=15, players}` → 本地建世界、进入 `PLAYING`。
- `OVER` 后房主点「再来一局」→ 新 `seed`、`wave=1`、`score=0`、重新 `lock(true)`。
- 非房主只显示「等房主开始/再来一局」。

### 8.4 离开 / 踢人

- 主动离开走 `LEAVE`，回大厅。
- 房主踢人走 `KICK`；被踢者收到 `KICKED` + 4002 关闭，不可用原会话恢复。
- 队友离开后，主机把该玩家从世界移除（或标记观战）；其他人看到成员列表变化。
- 房主离开：`HOST` 事件转移给最小 slot 在线成员；其他客户端本局作废回大厅。

## 9. 客户端预测、插值、外推与校正

### 9.1 自己的飞机：本地预测

- 指针更新 `aim` 后，本地每帧跑 §4.2 的 `seek`，飞机立即响应，不等服务器。
- 主机快照里也有自己的位置；以主机为准做校正：
  - 误差 ≤ 24px：每帧向快照位置靠 20%（`pos += (snap - pos) * 0.2`），视觉平滑。
  - 误差 > 24px：快速插值（50%/帧），避免追太久。
  - 误差 > 96px（重生/传送/严重卡顿）：直接吸附到快照位置。
- 因为双方用同一套 `seek`，误差主要来自 RTT（300px/s × 50ms ≈ 15px），校正不会明显可见。
- 判定半径只有 4px，视觉上「擦弹」更宽容，掩盖误差。

### 9.2 队友和敌机：插值

- 保留最近 5 帧快照（按 `tick` 排序，带本地到达时间）。
- 渲染时钟取 `now - 80ms`，找包住它的两帧，按时间比例插值：
  - 玩家按 `slot` 匹配（快照里一定存在）；
  - 敌机按 `id` 匹配（新 id 直接出现在插值起点，消失即播放爆炸）。
- 插值只用于玩家/敌机；它们数量少、移动慢，线性插值足够。
- 如果只拿到一帧：直接用该帧位置，不退化成闪烁。

### 9.3 子弹：外推

- 子弹数量大，不做 id 匹配和跨帧插值；直接用**最新快照的位置 + 速度**外推：
  ```
  renderX = snapX + vx * (renderAt - snapArrival) / TICK_MS
  renderY = snapY + vy * (renderAt - snapArrival) / TICK_MS
  ```
- 外推上限 150ms；超过就停在最后位置（表现为轻微卡顿），不无限飞。
- 敌弹/我弹都用同一规则；我弹按 `ownerSlot` 上色。
- 子弹出界即不画；快照里本来也会被回收。

### 9.4 自举（漏掉 START）

- 客户端收到第一帧 `phase=playing` 的快照时：清空快照缓冲、按 `playerCount/players` 初始化玩家、进入 `PLAYING`。
- 所以 `START` 丢失不影响对局，只是少了一次「换局」的即时反馈。

### 9.5 tick 与陈旧帧

- 只接受 `tick` 比 `lastAppliedTick` 大的快照，**用 u32 无符号差值**（`tick` 可能大于 2^31）：
  ```js
  if (lastAppliedTick >= 0) {
    const d = (snapTick - lastAppliedTick) >>> 0;
    if (d === 0 || d >= 0x80000000) return;  // 旧帧/重复帧，丢弃
  }
  lastAppliedTick = snapTick;
  ```
- 重连补发的帧可能比本地已应用的旧，直接丢弃；新帧继续。
- `START` 与重连成功（`resumed`）时清空快照缓冲并重置基线；因为快照是全量状态，下一帧就能重建。
- `RESYNC` 时清空插值缓冲，保留 `lastAppliedTick`（继续丢弃旧帧），等下一帧全量。

### 9.6 状态指示

- 右上角显示「延迟/快照年龄」：`now - lastSnapshotArrival`。
  - < 250ms 正常；
  - 250–600ms 黄色「网络抖动」；
  - > 600ms 红色「等待房主」。
- 本地预测始终运行，网络差时先表现为队友/敌机卡顿，而不是自己不能动。

## 10. 断线、重连、RESYNC、房主切换、暂停

### 10.1 队友断线

- 中继在宽限期（60s）内只广播 `PEER_OFFLINE`，不广播 `PEER_LEAVE`。
- 主机把该玩家 `flags.bit0` 置 0：位置保留、不受击、不开火；快照继续下发。
- 玩家回来：`PEER_REJOIN`，主机置回在线，给 60 tick 无敌；槽位不变。
- 超过宽限期：`PEER_LEAVE{reason=TIMEOUT}`，主机移除该玩家；剩余玩家继续。

### 10.2 补发与 RESYNC

- 重连：`RelayClient` 带 `sid + lastSeq` 恢复；服务端从 64KB 环形缓冲补发命中的帧，再发新帧。
- 补发窗口约 2–4s（最坏快照 15Hz × 1.9KB ≈ 29KB/s，64KB 约 2.2s；典型 3–4s）。
- 超窗：服务端发 `RESYNC{seq, reason}`，不补发；客户端清空插值缓冲，等下一帧全量快照即可。
- 因为快照是全量，**不需要**像猜数字那样再发 `sync_req` 请求快照。
- 重连成功时会清空快照缓冲并重置 tick 基线；`START` 也会重置，避免主机切换/时钟偏差让新快照被误判成旧帧。
- 补发帧里可能混有旧局/旧 tick 的快照，按 §9.5 丢弃。

### 10.3 主机断线 / 离开

- 主机临时断线（宽限期内）：
  - 其他人 600ms 收不到快照 → 显示「房主断线，等待重连…」，本地暂停输入上送；
  - 主机的世界还在内存里，重连（带 sid）后继续发快照，其他人自动恢复。
- 主机真正离开 / 超时：
  - 中继把房主转给最小 slot 的在线成员，广播 `HOST`；
  - 所有客户端收到 `HOST` 且当前不是 `LOBBY` → 本局作废、回大厅，提示「房主已离开，本局结束」；
  - 新房主可以重新开局。**不做世界迁移**：新房主没有旧世界，迁移要额外快照握手，v1 不做。

### 10.4 主机切后台 / 暂停

- 主机用 30Hz `setInterval` 驱动模拟（rAF 只负责渲染，后台/headless 里 rAF 可能被挂起）；`document.visibilitychange` 隐藏时**显式暂停**，恢复时重置累积器再继续。
- 队友不依赖暂停消息：快照饥饿 600ms 即显示暂停遮罩；恢复收到快照后自动消失。
- 队友切后台：只影响自己的渲染，回来后跳到最新快照；不会暂停主机。

### 10.5 刷新页面

- `sid` 只在内存里，刷新 = 新会话、新 slot；旧 slot 在宽限期内仍占位，房间可能短暂满员/锁房。
- v1 明确：**刷新 = 本局作废，重新加入**（与猜数字一致）。
- M2 可选：`sessionStorage` 存 `sid + 最近一帧快照`，刷新后尝试 `RESUME` 并恢复画面；世界由主机快照续上。

### 10.6 其他异常

| 现象 | 原因 | 处理 |
|---|---|---|
| `BAD_TARGET` | targets 里有刚离开的成员（竞态） | 丢这一帧，不重连；刷新成员列表后下一帧正常 |
| 1013 慢消费者 | 发送队列 256KB 溢出 | 自动重连 + 全量快照恢复；必要时降低画质/帧率 |
| 4004 会话失效 | 宽限期超时 / 被踢 / 被新连接替换 | 回大厅，提示重新加入 |
| 4005 服务端退出 | 进程关闭 | 回大厅，提示稍后重试 |
| 4006 限流 | 入站超过 200 帧/s | 退避；正常游戏不会触发（本端 30–45 帧/s） |
| `ROOM_LOCKED` | 第 5 人 / 对局中 | 提示等下一局 |
| `ROOM_NOT_FOUND` | 房间销毁 | 不重试，回大厅 |
| 页面没更新 | `go:embed` 是编译期烘焙 | 重新 `go build` / `go run`（见 §13.5） |

## 11. PvP 扩展设计（M3 预留）

### 11.1 复用

- `START.mode = 1`；`SNAP` 里仍用同一套玩家/子弹字段，敌机段为空、`bossHp=0`。
- 输入仍然只有目标点：PvP 的朝向/开火由主机**自动瞄准对手**，避免改 `INPUT` 格式。

- 2 人；各自 3 HP、3 命；先打光对方命数者胜；BO3。
- 无小怪，中间刷掩体/道具（M3 再定）。
- 主机权威判命中，和 PvE 同一套子弹碰撞。

### 11.3 主机优势与缓解

- 主机输入 0 延迟，队友有 RTT；PvP 下不公平。
- 缓解（按顺序尝试）：
  1. BO3 + 每局轮换房主/先后手；
  2. 给主机输入加固定延迟（约平均 RTT/2），用同一套 `seek` 目标点实现；
  3. 仍不满意则只在朋友间娱乐，不做竞技。
- 不改协议；以上都在主机模拟层实现。

### 13.2 唯一 Go 改动

```go
//go:embed index.html relay.js bulls.html bulls-core.js bulls.js

```

实现轮改成：

```go
//go:embed index.html relay.js bulls.html bulls-core.js bulls.js plane.html plane-core.js plane-net.js plane.js
var FS embed.FS
```

- 只加文件名；`internal/` 与 `cmd/` 一行不动。

### 13.3 其他非服务端改动

- `Makefile`：`test-js` 加两个 Node 用例；新增 `e2e-plane`、`ui-plane`。

- `docs/CONTEXT.md`：实现落地后再补「已交付」段落。

### 13.4 运行方式（实现后）

```bash
go run ./cmd/server          # 或 make run
# 本机：http://localhost:8080/plane.html
# 手机（同一局域网）：http://<电脑IP>:8080/plane.html
```

- 页面默认连 `ws://<当前 host>/ws`；前后端分开部署时在 `web/config.js` 里填 `wsUrl`，或用 `?ws=ws://<host>:8080/ws` 临时覆盖（优先级：`?ws=` > `config.js` > 同源）。
- 如果站点是 https，必须用 `wss`；反代要放行 `Upgrade`。

### 13.5 严格零后端改动的备选

如果哪天要求「一个 Go 文件都不能动」：

- 用任意静态服务器托管 `web/`（例如 `python3 -m http.server 8000 --directory web`），打开 `http://<host>:8000/plane.html?ws=ws://<host>:8080/ws`；或把后端地址写进 `web/config.js` 后直接打开页面。
- 浏览器 WebSocket 不受 CORS 限制，服务器 `CheckOrigin` 当前放行；只要 `?ws=` / `config.js` 指对即可。
- 这条路径不需要改 `embed.go`，但多一个静态进程；默认仍推荐 embed 一行，少一个部署件；正式分离部署见 [部署指南](deploy.md)。

### 13.6 模块接口（实现轮按此落地）

`plane-core.js`（纯函数，可 Node `require`）：

- `newWorld({ seed, players, maxWave, tick0 })`（`tick0` 可选，主机传入单调基线）
- `step(world, dtTicks = 1)` — 推进一个 tick
- `setAim(world, slot, x, y)` — 主机收到 INPUT 后写入
- `removePlayer(world, slot)` / `setConnected(world, slot, online)`
- `findPlayer(world, slot)` / `bossOf(world)`
- `spawnEnemy` / `addEBullet` — 波次与测试用
- `worldHash(world)` — 测试用稳定哈希

`plane-net.js`：

- `TYPE = { INPUT: 1, SNAP: 2, START: 3 }`、`MAGIC = 0x50`
- `encodeInput({ x, y, flags }) → Uint8Array`
- `encodeStart({ seed, mode, maxWave, players }) → Uint8Array`
- `encodeSnapshot(world) → Uint8Array`
- `decode(bytes) → { type, ... }`，未知 magic/type 返回 `null`，截断抛 `RangeError`

### 13.7 实现陷阱

1. **targets 必须包含全员（含自己、含离线）**，否则 `seq` 空洞 → 4000 重连。
2. **自己的回显必须按 `from === selfSlot` 忽略**，不要把 echo 再应用一遍。
3. **快照必须全量**；一旦做 delta，RESYNC 就要额外的快照握手。
4. **`tick` 跨局不重置**；上一局补发帧靠 tick 丢弃。
5. **主机模拟不要用 rAF 空转**：隐藏时显式暂停，恢复时重置累积器。
6. **输入只送目标点**；主机自己做 `seek` 和边界钳制，别直接赋值位置。
7. **改 `web/` 后必须重新 `go build`**，`go:embed` 是编译期烘焙。
8. **`BAD_TARGET` 不重连**：成员离开的竞态，丢一帧即可。
9. 用 `relayBytes(Uint8Array)`，不要 `relay(obj)`（后者会 JSON 化）。
10. 二进制编解码在 Node 测试里可直接跑，不要依赖 DOM。

## 15. 风险、已知限制与排错

### 15.1 风险与取舍

| 风险 | 影响 | 缓解 |
|---|---|---|
| 主机切后台 | 全场暂停 | 显式暂停 + 队友 600ms 饥饿遮罩；提示房主保持页面可见 |
| 刷新页面 | 本局作废 | v1 接受；M2 `sessionStorage` 恢复 |
| 主机可作弊 | 改分/改血 | 项目既定边界；不做竞技/付费 |
| 预测/判定误差 | 擦弹被判定命中 | 4px 判定半径 + 软校正；M2 输入历史/回滚 |
| 手指遮挡飞机 | 移动端手感 | M1 接受「落后于手指」；M2 偏移/摇杆 |
| 实时局带宽/写次数 | 单节点容量远低于桌游目标 | 按 200–500 房压测；必要时降快照频率/子弹上限 |
| 环形窗口短 | 断线 > 2–4s 需 RESYNC | 全量快照自愈；UI 提示「重新同步」 |
| 移动端性能 | 4 人局 135 帧/s 入站 | 解码零分配、渲染对象池、限制实体数量 |
| `go:embed` 不更新 | 页面旧行为 | 改 web 后重新 build/run |
| 反代超时/WS 升级 | 连不上 | 空闲超时 > 20s，放行 Upgrade；https 用 wss |
| 主机离开无迁移 | 本局作废 | v1 明确；M4 再评估世界迁移 |

### 15.2 排错

| 现象 | 先查 |
|---|---|
| 页面打不开 | 是否重新 `go build`；`plane.html` 是否加进 embed |
| 连不上 `/ws` | 反代 Upgrade；http/https 与 ws/wss 是否匹配；`?ws=` 是否正确 |
| 飞机瞬移 | 是否把 `aim` 直接赋给位置，或 `step` 没取 `min(dist, maxSpeed*dt)` |
| 自己不能动 | 本地预测是否被快照硬拉回；校正阈值是否太小 |
| 频繁重连 | targets 是否漏了自己/离线成员；`seq` 是否连续 |
| 队友看不见彼此 | 输入/快照是否 broadcast 全员；`from` 过滤是否写错 |
| 画面卡一下 | 快照饥饿/GC；看 `snapshotAge` 与实体数量 |
| 手机不能拖 | `touch-action`、`preventDefault`、pointer 事件是否被页面滚动抢走 |
| 主机断线后无法恢复 | 是否误做了「主机迁移」；v1 应回大厅由新房主重开 |

### 15.3 未决问题（实现前可再确认）

- 移动端是否要「手指偏移」而不是绝对跟随（M1 先绝对跟随，实测再定）。
- 4 人上限是否足够；若要 6 人，快照/带宽按 `N²` 重算，需要先压测。
- 是否需要音效与震动反馈（M2）。
- PvP 的主机优势用「延迟补偿」还是「轮换房主」（M3 实测再定）。
